PROJECT OBJECTIVE
════════════════════════════════════════════════════════════════════════════════
Remove all draft products from mockData.products and establish complete 
separation between the Products and Requests concepts in the system.

RATIONALE
════════════════════════════════════════════════════════════════════════════════
The system now follows a clear data model:

  PRODUCTS: Real, published items in the system
  - These are items currently available/active in the marketplace
  - Statuses: active, passive, rejected
  - Can have update requests submitted

  REQUESTS: Supplier submissions for new products or changes
  - These are proposals/submissions from suppliers
  - Must be approved by admin before affecting products
  - Types: product_create, product_update, stock_price_update
  - No immediate impact on actual products

KEY INSIGHT: Requests are NOT products - they are reflections/submissions.

NEW BUSINESS LOGIC
════════════════════════════════════════════════════════════════════════════════

New Product Creation:
  1. Supplier submits product_create request
  2. Request stored in mockData.requests (status: submitted)
  3. Admin reviews in "Yeni Ürün Talepleri" tab
  4. Admin approves → product added to mockData.products
  5. Product now available in the system

Product Update:
  1. Supplier submits product_update request for existing product
  2. Request references product but doesn't modify it
  3. Product remains unchanged until request approved
  4. Admin approves → existing product data updated
  5. Changes now live in the system

KEY PRINCIPLE: Requests are NEVER automatically applied. Admin approval is 
required to convert requests into actual product changes.
